# 改稿实践与向改稿学习：按目标精修，持续沉淀经验

单独改稿使用 `topmind-revise`；其他写作技能成稿自查时同样适用本页原则。短文本一次通读与核对即可完成，长文深改可分步推进，无需机械执行固定十步流程。

---

## 一、从修改目标选择动作

| 目标 | 可用动作 | 验收标准 |
|---|---|---|
| **像新闻稿 / 没钩子** | 把核心结果、反差数字或真问题提到第一句；砍掉门槛、花絮与公文头衔 | 读者第一眼知道跟自己有什么关系 |
| **AI 味重 / 像完成任务** | 删元话语、删说教收尾与金句、把讲师命令改成邻座商量、参数译成体感 | 读起来像跟朋友说话，点到即停 |
| **太长 / 信息淹没** | 删重复、压背景、砍次要细则（留给另篇）、并列项转紧凑 `1）2）` | 干货原件与适用边界完整，废话清零 |
| **太平 / 没记忆点** | 补具体对象点名、换算日常账单、给事件起短称呼、用画面或对话代替评论 | 作者声音鲜明，事实与确定性未变 |
| **评测 / 观点被洗平** | 恢复作者原稿的个人口吻、实测褒贬与具体观察维度；仅减弱无据绝对因果 | 既有真人态度，又不夸大未证实事实 |
| **只要排版** | 调整段落空行、列表符号与纯文本呈现（转 `topmind-format`） | 原文措辞、数字、标点与语义符号完全保真 |

## 二、如何向作者的改稿学习（核心进化机制）

向作者亲手改过的稿子学习，比背诵一百条禁令更有效。复盘或吸收作者改稿时遵守以下八条原则：

1. **先列「删了什么、加了什么」，再总结机制**  
   不要只看「改后更短或更冲」就当模板抄。看作者删掉了哪些负担（通常是新闻导语、元话语、购买门槛、发布会致谢、说教收尾、虚指群体、讲师命令），又加上了什么（反差钩子、短称呼、具体点名、能照做的原件、适用与禁用边界、真疑问）。
2. **作者自己补上的「我」，下一篇绝不替他代写**  
   作者定稿时自己加上「我看到」「刚打开试了下」，是因为他当时真在现场。助手下次起草同类稿件时，依然只能写「有人实测」「官方文档写着」「现在打开列表看一眼」，把第一人称现场留给作者本人。
3. **已被认可的好稿，不为「更像爆款」而大改结构**  
   如果初稿的钩子、算账或切口已经获得作者认可（「这版很好，很有真实感」），后续只做段落拉开、标点落点等微调，绝不推翻重写或画蛇添足塞入新套路。
4. **同一组事实，开口不同就是两篇完全不同的帖子**  
   把关键结果（如「主动重构比例从 10% 涨到 50%」）埋在第三段并加比喻升华，是普通摘要；把反差结果直接变成第一句问句，紧接原句提示词、适用场景和「只想小改就别加」的边界，就是高收藏干货帖。
5. **保留个人口吻，不等于保留无据绝对因果**  
   作者原稿写「仔细聊了一轮，感觉对认真做原创的作者绝对是更利好了」，修改时把过满的「绝对」收为个人判断（「我倒觉得……未必是坏事 / 感觉更有利」），补上「开源代码参数变化 ≠ 线上已全面调整」的事实边界，但**必须保留「仔细聊了一轮 / 我倒觉得」的真人温度**，不能洗成冷冰冰的通稿。
6. **单轮修改意见必须标注适用范围**  
   例如：为某款插件公众号定的「标题点名插件 + 开头写安装与痛点 + 功能列表 + 小标题配例子截图」，只适用于「介绍/推荐工具或插件」类文章；「简单直观的功能不长篇讲道理」适用于直观功能说明，不能外推去砍掉复杂原理文或争议评测文的必要限定。
7. **绝不伪造「改前原文」或冒充终稿**  
   只有写法方向或助手建议稿时，如实标明「写法示例 / 建议稿（非终稿）」，不虚构改前靶子，也不把未确认的建议稿当成作者已发终稿。
8. **同样重视负反馈**  
   当作者反馈「太小众学术化，不够话题性，偶尔发可以」或「同题拆三个切口还是太集中」，说明细节有趣不等于大众有话可接，选题与排期需主动拉开梯度。

## 三、如何把新经验与思考方便地扩展进技能库

当在创作或改稿中沉淀出新的有效策略、体裁思考或典型对照时，可按以下轻量方式随时扩展：

1. **提炼四要素**：`适用场景（Scope）` → `核心机制（Mechanism）` → `具体示例或改前改后对照（Example）` → `例外与边界（Limits）`。
2. **写入按需知识包**（见 [knowledge-library.md](knowledge-library.md)）：
   ```bash
   python3 scripts/knowledge.py add --pack <知识包目录> \
     --id <卡片ID> --title "<标题>" --summary "<一句话机制摘要>" \
     --skills "topmind-briefs,topmind-revise" --tags "<标签>" \
     --kind lesson --body <正文文件.md> --scope "<适用稿型与场景>" --limits "<何时别用>"
   ```
3. **先小范围验证再升格**：单次反馈先标清适用范围作为可选策略卡；经多次不同题目验证稳定后，再更新共享参考。

## 四、实际修改与辅助工具

对文件做实质修改前保留可恢复版本；聊天中的短文本直接交付修改结果。

```bash
python3 scripts/de_ai_lint.py 稿子.md
python3 scripts/revise_check.py 改前.md 改后.md --report 改稿报告.md
```

- `revise_check.py` 的数字、引语、确定性词变化和改动比例都是复查线索，帮助检查有没有误伤承重事实，不代表「改得多就是错」。
- `de_ai_lint.py` 的 `W/H/I` 提示均回到上下文判断，**不要求清零，也不用词面分数决定是否定稿**。
- 交付完成稿时，简要说明关键改动理由与待作者确认的未核实项即可；除非长文深改或用户要求完整审计，否则不必凑长篇报告。
