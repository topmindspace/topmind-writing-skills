# 公众号改稿规则（Stage 1 执行标准）

从技术博客 Markdown 到公众号稿，改的是**阅读节奏**，不是技术事实。事实、数据、链接一律不动。

## 必须做

1. **开头用具体事实**：接地气、好懂，不要背景铺垫，不硬凑对仗收句（`core-voice.md` V05）。原文首段若是长背景，压缩或后移。
2. **段落切分**：单段 ≤ 110 字（约 4 行手机屏）。长段按语义断点拆开，不要机械等分。
3. **小标题序号手写**：要序号就直接写「一、」「二、」，`md2wechat.py` 原样保留、不再叠加自动编号；整篇都没写序号时才按 `h2_style` 自动编号（规则见 `element-spec.md`「章节编号」）。
4. **列表项 ≤ 70 字**：超长列表项改成「加粗小标题 + 短说明」的段落组。
5. **重点加粗**：只用标准 `**加粗**`，留给结论句和关键数据；不写 `++下划线++` 等扩展标记（旧稿里有的照常渲染）。重点过多看强调占比（`lint-wechat.py` 超过 20% 提醒），见 `element-spec.md`「强调」。
6. **长句拆短**：单句 > 45 字且有逗号堆叠时，拆成两句。
7. **图注与来源**：图片说明写进 `![说明](images/xx.png)`；出处写在图片下一行「来源：……」，排版时渲染成灰色小字图注。不在图注里复述图片内容（W21）。
8. **外链处理**：保留可点性无意义，改为「来源：XXX（URL）」的灰色小字或直接写机构名。
9. **收尾**：默认不以问句结尾，不写「欢迎留言讨论」「点个关注」这类客服腔；最后一句给判断，换个角度说，生活化类比最稳；可以「总结来说 + 结论 + 一句口语收尾」（`core-voice.md` V10）。

## 不要做

- 不改技术事实、不改数据、不改评测结论
- 不删代码块（公众号读者需要可复制的配置/命令）
- 不把「我」改成「笔者」「作者」等腔调词，第一人称是这类文章的信任来源
- 不加「随着...的发展」「在当今时代」这类 AI 腔 / 八股开场
- 不加 emoji 堆砌的小标题
- 不为了凑字数注水，公众号长文 3000-6000 字是合理区间
- 中英文/数字之间忘了空格没关系（lint --fix 会补），但**别手动在代码和链接里加**

## 源稿不用容器（单源 Markdown）

源稿 `<文章名>.md` 要能被 Obsidian 和任何派生脚本直接读，所以**不用 `:::` 容器、callout（`> [!note]`）、`![[ ]]`**：

| 想表达 | 纯 Markdown 写法 |
|---|---|
| 一句话核心观点 | 单独成段 + 加粗，或 `> ` 引用 |
| 关键数据对比（如「62.7% vs 99.9%」） | 一句话写清对比，或数据图 + 「来源：」行 |
| 补充但不打断主线的信息 | 普通短段落，或 `> ` 引用 |
| 操作建议、风险提示 | 列表或加粗开头的短段 |

`lint-wechat.py` 对新源稿里的 `:::` 报错；旧交付包（`公众号稿.md`）只告警，`md2wechat.py` 仍能渲染旧容器。

## 去 AI 腔检查点

- 排比三连句（"不是 A，不是 B，而是 C"）出现超过 2 次 → 改写
- 「值得注意的是」「综上所述」「不难看出」→ 删
- 每段都以「首先/其次/最后」开头 → 打散
- 形容词堆叠（"极其轻巧稳定的架构"）→ 留一个

## 排版参数基线（调研印证的通用规范）

- 正文 16px、行距 1.75、字间距 0、左对齐（不用 justify，会被格式检测判为非标准值）
- 段间距 22px 代替首行缩进（手机端惯例）
- 正文色 #333（纯黑 #000 在白底上过刺眼），辅助文字 #888
- 代码块深底浅字（浅灰底代码块在部分安卓机型上对比度不足）

## 交付前自检

```bash
python3 scripts/lint-wechat.py --input <文章名>.md --fix
```

错误项（长段 > 200 字 / 图片缺失/过大）必须清零；警告项逐条判断是否接受。
