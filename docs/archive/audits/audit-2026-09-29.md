## 三、发现的问题（按严重程度，含 Proposal）

### 严重

**1. 版本号已分叉上线（需用户裁决，见第五节第 1 条）**
`topmind-cover/SKILL.md:3` 与 `topmind-x-article/SKILL.md:3` 写 `version: 1.0.0`，但各自 `package.json` / `CHANGELOG.md` / 根 README 技能表均为 `0.1.0`；`topmind-wechat-post` 的 `package.json` 为 `0.1.0` 但 SKILL.md 无 version 字段。三处"源头"已不一致且随 0.2.0 发布上线。门禁从不比对 `frontmatter version == package.json version`，这是穿过 CI 的直接原因。

**2. `bin/tms-skills.js` 安装守卫缺失（S1/S2，Proposal）**
- `--to` 指向 skill 自身目录 + `--force`：先 `rmSync` 删掉源目录，再"成功"安装空目录（数据丢失 + 虚假成功，实测复现）。
- `--to` 指向 skill 内部子目录：`copyDir` 无限递归复制直至 `ENAMETOOLONG` 崩溃并留下垃圾目录树。
- 修复需新增 src/dest 关系校验（相等或 dest 在 src 内则拒绝），属行为变更；且仓库无任何安装器自动化测试。建议：加守卫 + 补安装器负向测试（复用实测 case）后再修。

**3. Release workflow 无 tag ↔ package.json 版本交叉校验（Proposal）**
`.github/workflows/release.yml` 触发 `tags: v*`，publish 全程只读 `package.json` version。若误打 tag（如 v0.2.1 而 package.json 仍 0.2.0），npm 按 package.json 发布，`npm view` 已存在即视为成功 → 工作流绿色，tag 与 npm 永久错位，且幂等逻辑掩盖了它。建议 publish 前加 `[[ "${GITHUB_REF_NAME}" == "v$(node -p require('./package.json').version)" ]]` 校验。

## 四、安装模型分析：单一分发包 vs 每技能独立 npm 包

**现状（A）：单一分发包按技能名安装** — 一个 npm 包 `@topmindspace/tms-skills` 内含 4 个技能目录，用户 `npx @topmindspace/tms-skills install <skill-id>` 按需安装；tms-skills 本身是分发器不是技能。

| 维度 | A 单一分发包（现状） | B 每技能独立 npm 包 |
|---|---|---|
| 维护成本 | 低：一次打 tag、一条 release workflow、`sync_npm_files.js` 自动同步 files 清单 | 高：4 套版本号、4 条发布链、跨包依赖矩阵 |
| 版本管理 | 简单：整仓同 tag、CHANGELOG 一处；代价是粒度粗——任一技能改动即全包 bump，只能钉整包版本 | 精细：各技能独立演进、独立钉版本，互不拖累 |
| 用户体验 | 好：一个包名、一句命令、无需记多个包名；`list` 一览 4 技能 | 碎片化：4 个包名要记、npm 搜索分散、安装命令不统一 |

**建议**：4 技能同源、同节奏、共用门禁与发布链，现阶段 **A 明显更优**，继续保持。只有当某技能迭代频率或受众显著分化（如 top-ppt-html 独立大版本演进、或某技能需要独立发版节奏）时，才值得拆为 B。回答用户原问题：**不需要每次都装整个 tms-skills；现在就是按技能名单独安装**（`install top-ppt-html` / `install topmind-cover` 等），tms-skills 包只是载体。
