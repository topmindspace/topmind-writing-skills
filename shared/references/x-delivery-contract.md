# X 文本交付规约（必读必守）

> **适用范围**：X 短文与段子——`topmind-briefs` 的 X 版、`topmind-viral-posts`、`topmind-format`，以及 `topmind-wechat-post` 派生的 X 短帖。
> **不适用**：`topmind-x-article` 的 X 长文（`X长文.html` / `X发布稿.txt`）和公众号长文、briefs 的公众号版——长文里合理的文内链接照常保留；但长文的信源、原图、说明仍按第三节另列。
> 排版细则见 `x-post-format.md`，emoji 见 `emoji-system.md`，版式见 `x-layout-patterns.md`，去 AI 味与吸引力见 `writing-principles.md` 第五点五节。

## 一、短文工作流：先信源，后排版

顺序固定，前一步没做完不进下一步：

1. **核实信源**：找一手来源（官方博客 / 公告 / 论文 / 仓库 / 当事人原帖）。二手转述只作线索；厂商自报的数据写「官方称」「厂商口径」，传言、爆料写「据传」「未证实」，并写清发布时间（注明时区）。
2. **找原帖、原图**：原帖链接、官方图 / 截图 1–2 张。找不到原图就问用户要不要配图，不擅自生图。
3. **写内容**：一件事讲清楚，首行一句简单的话题陈述，具体数字和场景，人话，事实讲完就停；按 `core-voice.md` 和 `de-ai-rules.md` 过一遍。
4. **排版**：目标是方便阅读——合理分段（一段 1–3 行，段间空一行）、合理列表（3–7 条才用列表，2 条写成两句）。

段子（viral-posts）不必走 1–2 步的完整核实，但涉及事实和数字时同样要有出处，出处另发。

## 二、列表与 emoji

X 是纯文本，不渲染 Markdown。**两种体裁都禁用会被当成 Markdown 的列表**：`- ` `* ` `+ ` `1. ` `1)`（`lint_x_post.py` 报 E1 / E2）。

| | 短文体（briefs X 版、格式化成短文、热点短文版） | 段子体（viral-posts 段子、转段子） |
|---|---|---|
| 分点写法 | 任选一种、一帖一套：emoji 符号（🔹 / 1️⃣ / ✅ ❌）、全角序号「1）」、圆点「·」、【小标题】分节 | **不加任何符号**：一条一行，靠行间空行区分 |
| emoji | **不强制**。要用就用得合理，并且只用 TopMind 体系（`emoji-system.md`）：标题 emoji 0–1、人设点缀 0–2 | **完全不用**：无人设点缀、无情绪表情、无 emoji 列表符号 |
| 节奏 | 段落短、段间空一行；列表连续排，长条目间可空一行 | 每句、每条一行，行与行之间空一行 |
| 检查 | `lint_x_post.py 正文.txt` | `lint_x_post.py 段子.txt --duanzi`（出现 emoji 报 W13） |

列表前一行写「xx：」引导语。

## 三、交付：正文一段纯文本，链接、图片另发

**正文 = 一段可以原样发到 X 的纯文本。** 用户复制整段就能发，不用删任何一行。

| 属于正文 | 不属于正文（另发） |
|---|---|
| 标题行、正文、列表 | **所有链接**：来源 URL、原帖链接、参考链接 |
| 话题标签（末行，0–3 个） | **来源行**：「来源：…」「出处：…」「原帖：…」 |
| 短文体可选的标题 emoji 与人设点缀 | **原图、配图**、配图建议、图注、出图 prompt、`[图1]` 占位 |
| thread 的「1/3」序号（每条一段） | 内部分类标签、备选话题标签、排版说明、核实提醒、【帖 N】之类的块标题 |

规定：

1. **聊天交付分三条**：正文一条消息（或一个独立的 ` ```text ` 纯文本块）→ 链接一条（来源 / 原帖，每行「名称｜发布时间（时区）｜URL」）→ 图片一条（1–2 张原图，或「未找到原图，要不要配图？」）。最后可附一条说明（内部标签、改了什么、核实提醒）。缺的写「无」或省略，绝不糅进正文。
2. **正文里不出现 URL 和来源行**。出处在正文里只用文字点到（如「官方博客称」「据论文」），链接另发。
3. **多条帖子 / thread**：每条一个正文块；块名（「帖 1」）写在块外。
4. **原图**：`[图1] 图片地址或文件名 — 图注；来源` 写在图片那一条里；没有原图就问用户要不要配图（可选 `topmind-cover`），不擅自生图。
5. **公众号版**（briefs 双平台）单独一个 ` ```markdown ` 块；公众号和 X 长文可以有文内链接，不受第 2 条限制。
6. **落盘同理**：`X短文.txt` 只放正文；链接、图片、说明写进 `交付说明.md`。
7. **发前自检**：`python3 scripts/lint_x_post.py 正文.txt`（段子加 `--duanzi`）。E 类必须清零：E10 正文有 URL，E11 有来源行，E12 有配图说明 / 图片占位；W9 去 AI 味、W10 首行太长、W12 混入说明或内部标签、W13 段子出现 emoji。

## 四、聊天交付示例

正例（短文；产品与链接为虚构）：

````text
正文（直接复制）：
```text
某编辑器 3.0：补全延迟压到 200ms 以内（官方称）

这次改了三处：

1）补全延迟 200ms 以内，官方实测数据
2）一次改多个文件，不用来回切
3）免费版每月 50 次

写小脚本的人，免费额度基本够用；大仓库还得等第三方实测。

#AI编程
```

链接：
官方更新日志｜2026-10-13 09:00（UTC+8）｜https://example.com/changelog

图片：
[图1] https://example.com/images/release-3.png — 官方发布图；来源：官方更新日志
````

正例（段子，零 emoji，两条各自成块）：

````text
帖 1：
```text
这周把发帖流程压缩成三步：

早上先回评论

中午发一条原创

睡前回访新关注

三步走完，不焦虑

#日拱一卒
```

帖 2：
```text
说个冷知识：

收益不只看浏览量。

#创作者收益
```

链接：无（运营段子）
图片：未找到原图。要不要配图？可以用 topmind-cover 出一张 16:9 图。
说明（内部标签）：帖 1 类型=打卡日常型｜用途=日常；帖 2 类型=冷知识揭秘型｜用途=引流
````

反例（不要这样交付）：

````text
```text
【帖 1】
🆕 重磅！某编辑器 3.0 发布 🐔
- 更快、更强、更智能
来源：官方更新日志 https://example.com/changelog
配图：官方发布图
#AI编程
---
【帖 2】
...
```
````

错在：Markdown 列表 `- `；一个普通版本更新用「重磅！」是小题大做，「更快、更强、更智能」是排比套话；来源行和 URL、配图说明混进正文（应另发）；块标题进了正文；两条帖子用 `---` 拼在一个块里。段子里再出现 🐔 之类的 emoji 也算错。
